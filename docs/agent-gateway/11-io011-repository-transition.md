核对日期：2026-11-18。目标仓库：`https://github.com/zhing99-hash/io011`。

用户已确认：**本次只替换代码仓库，暂不操作服务器。** 不包含数据库迁移、账号导入、服务重启、域名切换、证书替换或生产部署。

## 1. 推荐结论

继续使用 IO011 仓库地址与历史，保留全部旧分支；从现有 main 建立新的替换分支，将本地企业 AI 连接平台放入该分支，通过 PR 审阅后合入。保留 agent-gateway 子目录及 docs/agent-gateway，减少移动源码造成的路径变化。

这属于仓库内容与产品方向的替换。旧版商家、商品、订单、购物界面等功能不自动包含在新版中；新版平台聚焦统一接口、身份、权限和数据接入，企业业务 Agent/工作流继续作为独立扩展。

本文件记录最初迁移方案与核对基线；执行记录见根目录 `MIGRATION-NOTES.md`。当前替换分支保留旧 main 的祖先关系；主分支合并与服务器部署另行处理。

## 4. 正式替换的执行顺序

1. **固定旧基线。** 重新读取远端各分支 HEAD，在记录中保存；先在本地为旧 main 和需要长期保留的旧版本建立备份分支或标签。远端引用的发布同样经过第 4 步的触发检查；名称若已存在，先核对指向，不强制覆盖。全部原分支保持原指向。
2. **建立替换分支。** 从当时的 main 建立 `next/enterprise-gateway`，如名称已存在则选新名称；保留其父提交关系，不新建无关历史，不 force push。
3. **按清单替换源码树。** 新分支中移除旧产品的当前跟踪项，加入新项目与根目录说明，保留 LICENSE；使用明确文件白名单，核对移除和新增列表，避免带入本机私有数据。
4. **补仓库级材料并记录发布边界。** 新 README 标明“开发预览”，补迁移记录、贡献说明及仅测试用途的 Windows CI，不加入部署步骤。独立分支推送与草稿 PR 由仓库维护者授权执行；记录可核验的仓库自动化。外部 webhook、部署平台及服务器自动拉取不能仅靠代码树证明，合并 main 前仍需核验，不承诺任意推送不会触发外部系统。
5. **在新检出中验证。** 按锁文件安装依赖，再运行 `node --preserve-symlinks --preserve-symlinks-main --test`；检查 README 链接、安装路径、示例配置、源码差异与私有文件排除。当前开发目录最近一次为 94 项通过，不能直接代替新检出的验收。
6. **通过发布触发检查后创建替换 PR。** 发布备份引用和替换分支，以 main 为 PR 目标，描述新定位、目录变化、历史保留、验证证据和“本次不部署”；PR 是具体可审阅结果。首次可保持 draft，先检查完整替换差异。
7. **满足服务器边界后合入。** 确认没有因 main 更新而自动改变旧服务器的部署链路后再合入。若外部自动拉取情况尚未确认，则保留替换分支/PR，暂不修改 main。不能因仓库中没发现 Actions 就推断服务器不会更新。
8. **以后独立安排部署。** 服务器切换、数据兼容、旧客户端迁移和生产验收另立工作项；本次不运行旧项目的部署脚本，不导入旧库，不发送服务重启命令。

## 5. 回退方式

替换分支在 main 合入前可直接停止，原 main 与所有旧分支不受影响。合入后如需恢复仓库内容，优先新增 revert 提交/PR，保留替换与回退的审计历史，不把共享分支强制重置到过去提交。

仓库回退不等于运行服务回退；本次没有服务器部署动作，因此也不把 Git 操作当作数据库/运行时恢复措施。归档分支或标签保留旧代码，不代表已经单独完成离线备份。

## 6. 替换完成的验收标准

- 原仓库 URL、旧分支和可追溯 Git 历史保留。
- 新分支中只有明确迁入的新平台代码、文档及仓库级材料，旧商业系统从新版目录移出。
- 没有新增实际环境变量、OAuth 密钥、运行数据库、隔离文件或依赖目录；公开测试证书单独标识。
- 新检出的依赖锁文件安装和测试通过，证据写入 PR。
- README、运行命令、客户端配置和目录链接按新仓库布局可用，保持开发预览状态。
- GitHub 合入前检查外部自动更新边界，整个任务没有直接改变服务器或数据库。
